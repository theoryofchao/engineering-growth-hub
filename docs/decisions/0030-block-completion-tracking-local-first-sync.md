# ADR 0030: Per-block/lesson completion tracking — local-first batched sync

## Status

Accepted. All three slices are built: backend, frontend local store + sync engine, and the checkmark/lesson-banner/jump-to-incomplete UI.

## Context

The user wants to mark individual content blocks ("slides") as read/complete with a checkmark, have the lesson's own completion derive automatically from its blocks, and have that state queue locally in the browser and batch-sync to the backend periodically rather than one request per click. This sits below the existing `UserProgress` model, which tracks coarser per-*section* mastery (`not_started`/`learning`/`practiced`/`mastered`) — this feature adds a new, finer-grained tier at the content-block level, not a replacement.

Three design points were decided with the user up front:
- Lesson-level completion is **derived** (all blocks complete ⇒ lesson complete), not a separately stored flag.
- Completion is **reversible** (unlike `UserProgress.advance_to`, which never downgrades).
- Sync is **debounced + periodic + best-effort on unload**, not purely manual or purely time-boxed.

## Decisions

1. **New `block_completions` table** (`app/models.py`): `id`, `content_block_id` (FK → `content_blocks.id`, `unique=True` — no `user_id` yet, same single-user-MVP posture as every other table in this schema), `completed_at` (nullable `DateTime(timezone=True)`; `NULL` = not completed, a timestamp = completed), `updated_at` (`DateTime(timezone=True)`, not nullable). Reversibility is just toggling `completed_at` between `NULL` and a timestamp — no separate status enum needed. `ContentBlock` gained a `completion` relationship (`uselist=False`, mirroring its existing `note` relationship).
2. **`updated_at` is stamped from the client's own clock reading at toggle time, not server receipt time.** This is the field the batch-sync endpoint uses for last-write-wins conflict resolution (e.g. two tabs toggling the same block, or a retried flush arriving out of order) — comparing by client logical time rather than arrival order means a delayed retry can never clobber a toggle that already landed more recently. A `_as_aware()` helper normalizes naive vs. tz-aware datetimes before comparing, because SQLite (used by the test suite) round-trips `DateTime(timezone=True)` as naive while Postgres keeps it tz-aware — this was caught by `test_batch_ignores_stale_write` failing with a `TypeError` before the fix.
3. **Lesson completion has no stored column.** `GET /api/v1/learning-sessions/<id>/completions` returns the state of every block in the session (including untouched ones, as not-completed) via `completions_service.get_completions_for_session`; the frontend (next slice) derives "lesson complete" by checking all entries are `completed: true`.
4. **New `completions_service.py`** — the one exception to this codebase's "simple CRUD lives directly in the route, no service file" convention (as seen in `notes.py`), because the batch endpoint needs to bulk-fetch existing rows for all blocks in one query rather than one `get_or_create` round-trip per item, which the per-item static-method pattern (`Note.upsert`, `UserProgress.get_or_create`) doesn't support efficiently.
5. **`POST /api/v1/content-blocks/completions/batch`** accepts `{"completions": [{"content_block_id", "completed", "client_updated_at"}, ...]}`, validated by a new Pydantic request schema (`BlockCompletionBatchRequest` — this codebase's first Pydantic-validated *request* body; every prior route hand-validates a plain dict, per `notes.py`). Validates every `content_block_id` exists in one query before writing anything (raises `ValueError` → 404 if not, matching the `study_sessions_service.py` convention of raising `ValueError` for bad input). Returns the canonical post-merge state for every item, including ones whose write was rejected as stale, so the frontend sync engine can reconcile its local queue either way.
6. **New `completions_bp` blueprint** (`app/routes/completions.py`), registered in `app/__init__.py` alongside the others — no route-registration pattern changes.
7. **Migration** `6f7371823939_add_block_completions_table.py`, generated via `flask db migrate` against the live dev Postgres container and hand-tidied (quote style, dropped the autogenerate comment markers) to match the rest of the migration history; chains from the existing head (`e47746f88a8c`).

## Consequences (backend slice)

- `pytest`: 92 passed (85 before this slice + 7 new, in `tests/test_completions.py`), including coverage for defaulting to incomplete, mark/unmark, multi-block batches, stale-write rejection, missing-block 404, and malformed-body 400.
- Verified against the live dev stack (`docker compose`, real Postgres) via `curl`: `GET .../completions` returns all three blocks of a real lesson as not-completed; a batch mark persists and is reflected on a subsequent `GET`; a batch write with an older `client_updated_at` than the stored one is correctly ignored (confirmed the `completed: true` state survives the stale write attempt). Test data was reset to its prior unmarked state afterward.

## Decisions (frontend local store + sync engine slice)

8. **`lib/completion-store.ts`** owns the `localStorage` queue (key `egh:block-completions`, following the existing `egh:` prefix convention): a `Record<blockId, {completed, updatedAt, dirty}>`. `toggleCompletion` flips a block and stamps `updatedAt` from the client's own clock (the same field the backend uses for last-write-wins). `hydrateFromServer` applies the server's baseline on load but never overwrites a `dirty` (unsynced) entry — the local optimistic value wins until it's actually flushed. `markSynced` applies a flush's result but checks the entry's `updatedAt` hasn't moved since it was read for that flush; if a newer toggle queued while the request was in flight, the confirmation is skipped rather than clobbering the newer write, which stays dirty for the next flush.
9. **Snapshot caching to avoid a `useSyncExternalStore` instability bug**: naively re-parsing `localStorage` into a fresh object on every `readAll()` call would return a new reference every time even when nothing changed, which `useSyncExternalStore` can treat as "store is tearing" (React warns about, and can loop on, an uncached snapshot for object/array state — unlike the existing scalar-valued hooks like `use-default-view-mode.ts`, which don't hit this because string equality is referential-equality-safe). Fixed by caching on the raw stored string and only re-parsing/re-allocating when it actually changes.
10. **`lib/completion-sync.ts`** implements the three agreed triggers: `scheduleDebouncedFlush` (resets a 5s timer per toggle), `startPeriodicFlush` (a 2-minute safety-net interval, returns a stop function), and `flushViaBeacon` (best-effort, for `visibilitychange`/`pagehide`, via `navigator.sendBeacon` since a normal `fetch` can get cancelled mid-unload). `flush()` guards against overlapping requests with an in-flight flag; a failed or rejected flush simply leaves entries dirty for the next trigger to retry — safe because the batch endpoint is idempotent.
11. **`hooks/use-block-completions.ts`** (reactive map + `toggle`, for the slide/block checkmark UI) and **`hooks/use-completion-sync.ts`** (mounts the periodic timer and unload listeners once) are built but not yet wired into any component — that wiring is slice 3's job, alongside the actual checkmark/banner/jump-to-incomplete UI.

## Consequences (frontend local store + sync engine slice)

- `vitest run`: 171 passed (143 before this slice + 28 new, across `completion-store.test.ts`, `completion-sync.test.ts`, and `use-block-completions.test.ts`), covering toggle/dirty/hydrate/markSynced merge semantics, debounce coalescing, periodic-interval start/stop, in-flight-flush dedup, stale/failed-flush retry-ability, and `sendBeacon` behavior (including when unsupported). `tsc --noEmit`, `eslint`, and `prettier --check` all clean.
- No UI changes this slice — `use-block-completions.ts` and `use-completion-sync.ts` had no callers yet.

## Decisions (checkmark UI slice)

12. **`ContentBlocks` takes a new required `learningSessionId` prop** (threaded through from `lesson-content.tsx`, which already fetches the session and knows `data.id`) and fetches `GET /api/v1/learning-sessions/<id>/completions` once on mount to call `hydrateFromServer`. This is an independent fetch-on-mount inside a client component, the same style `pomodoro-timer.tsx` already uses for its own state — not a second fetch bolted onto `use-fetch.ts`'s single-purpose hook.
13. **A `CompletionToggle` button** (small inline-SVG checkmark circle, same "no new icon library" posture as the settings gear in `site-settings.tsx`) is the one piece of UI reused in three places: per-block in page view, for the current slide in slide view, and nowhere else. `useBlockCompletions()` supplies the reactive map and a `toggle()` that both flips local state and schedules the debounced flush.
14. **Lesson completion and the "X/Y complete" count are computed in the render, not stored in state** — `completedCount`/`allBlocksComplete` are derived directly from `completions` each render, consistent with decision 3 (no stored lesson-level flag). The count and a "Lesson complete ✓" banner sit in the shared toolbar/header above both view modes, so they're visible regardless of which view is active.
15. **"Show only incomplete"** (page view) is a plain, unpersisted `useState` — unlike "Show section boundaries" it has no site-wide default, since the user didn't ask for one and this keeps the slice scoped to what was asked. It filters which blocks render, not the underlying `blocks` state, so note-taking/exercise state for a hidden block isn't affected.
16. **"Jump to next incomplete slide"** (slide view only) searches forward from the current slide index, wrapping around, and is hidden once `allBlocksComplete`. Page view has no equivalent jump control — "Show only incomplete" already answers "what haven't I done" there without needing one.
17. **`CompletionSyncMount`** (renders `null`, calls `useCompletionSync()`) is mounted once in `RootLayout` next to the existing `SiteSettings` global client component, giving the periodic-flush and tab-hide/unload triggers an app-wide lifetime independent of any one lesson page.

## Consequences (checkmark UI slice)

- `vitest run`: 177 passed (171 before this slice + 6 new in `content-blocks.test.tsx`, covering toggle-updates-count, toggle-back-off, the incomplete filter, the lesson-complete banner, and jump-to-incomplete appearing/disappearing). `tsc --noEmit`, `eslint` (one pre-existing, unrelated warning on an arrow-key effect from before this ADR), and `prettier --check` all clean.
- Verified against the live dev stack (`docker compose`, real Postgres) with a real browser (Playwright): checking a block in page view updates the count; "Show only incomplete" hides it; switching to slide view, using "Jump to next incomplete slide" and checking the remaining two blocks reaches 3/3 and shows the "Lesson complete ✓" banner with the jump control gone; reloading the page after the 5s debounce window shows the same 3/3 state, confirmed independently against the `GET .../completions` response. Zero console/page errors.
- **A real last-write-wins edge case was hit and diagnosed during this verification, not a code bug**: an earlier manual `curl` test (slice 1) had left `block_completions` rows with `updated_at` stamped `23:59:59` *that same day* — later than the real wall-clock time the later browser test ran at — so the backend correctly rejected the browser test's genuine, newer-in-real-time toggle as "stale" by the stored (but artificially-forward) timestamp. Resolved by deleting those leftover rows directly in Postgres rather than fighting through the API (an API-level "reset" is itself subject to the same last-write-wins rule, so it can't reliably override a stuck-in-the-future timestamp). No code change resulted; this is the conflict rule working as designed, and the DB was left clean afterward.
