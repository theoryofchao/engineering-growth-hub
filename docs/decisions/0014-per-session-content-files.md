# ADR 0014: One file per learning session, one directory per topic

## Status
Accepted

## Context
User feedback, opened right after ADR 0012 added a 6th session to `ai-assisted-software-development.json`: the per-topic JSON files were getting too large (806 lines / 88KB for that one file, and growing every time a session is added), and file organization should change to smaller files with names that meaningfully reflect the new structure.

A single flat file per topic (`content/curriculum/<topic-slug>.json`, holding `domain` + `module` + `topic` + the full `learning_sessions` array) was the Milestone 1 shape from ADR 0002/0004. It has no natural size ceiling: every new session appends to the same file, so a topic that eventually has 10+ sessions would carry all of them in one multi-thousand-line JSON blob — harder to open, harder to diff in review, and harder to point an agent or a human author at "just this one session" without them reading the whole topic first.

## Decisions
1. **Each topic is now a directory**, named after its slug (e.g. `content/curriculum/ai-assisted-software-development/`), not a single file. It holds:
   - `topic.json` — just the `{domain, module, topic}` metadata that used to be the first three keys of the flat file.
   - One file per learning session — e.g. `01-coding-agent-habits.json`, `06-native-toolkit-mcp-skills-hooks-lsp.json` — each holding exactly the session object that used to be one entry in `learning_sessions[]` (title, sequence, duration_minutes, objective, content_blocks, etc.).
2. **Filenames are hand-chosen short slugs, not auto-slugified full titles.** A mechanical slugify of e.g. "Scaling Up: Loops, Worktrees, and What a Real Company's Playbook Looks Like" produces an 80-character filename that doesn't actually help anyone scan a directory listing; `04-scaling-loops-and-worktrees.json` does. The leading zero-padded sequence number keeps directory listings in lesson order for humans, but is cosmetic — the session's own `sequence` field inside the file is still the only thing the loader trusts for ordering (same as before: `apps/api/app/seed.py` always derived block/exercise order from array position, never filename).
3. **`apps/api/app/seed.py` rewritten accordingly**: `load_file(path)` (one flat file in, full topic out) became `load_topic_dir(dir_path)` (one directory in: reads `topic.json` for domain/module/topic upsert, then globs every other `*.json` in the directory — sorted, any name — loading each as one session via a new shared helper, `_load_session(topic, session_data)`, factored out of the old per-session loop body so it's identical logic regardless of which file a session came from). `seed_all()` now iterates subdirectories of `content/curriculum/` instead of globbing `*.json` directly; `curriculum-map.json` (a file, not a directory) is unaffected since the iteration only recurses into directories.
4. **Migrated both existing topics** (`ai-assisted-software-development`, 6 sessions; `frontend-engineering`, 1 session) to the new layout and deleted the old flat files. Verified the migration was lossless before deleting anything: loaded both the old flat file and the new topic.json + session files back into Python and asserted structural equality (`topic.json` fields == old file's `domain`/`module`/`topic` keys; concatenated, sequence-sorted session files == old file's `learning_sessions` array) — not just "it looks the same," an actual equality assertion — before running `git rm` on the originals.
5. **`content/curriculum/README.md` rewritten** to document the new layout (directory tree, what `topic.json` holds, what a session file holds, the filename-vs-`sequence` distinction) ahead of the sizing rule ADR 0013 already added there, so both — "how files are organized" and "how big each one should be" — live in the one doc a content author actually opens.

## Consequences
- `pytest`: 29 tests pass unchanged — no test referenced `load_file`, `CONTENT_DIR`, or any file path directly; all went through the public `seed_all()` entry point, so the internal rewrite was invisible to them.
- Verified against the live stack: reseeded from the new directory structure against the same running Postgres instance used for ADR 0012's verification, and confirmed via direct SQL that session/block/exercise counts for `70-ai-assisted-software-development` are byte-identical to the pre-migration counts (7/6/6/6/6/7 blocks, 6/5/7/7/4/6 exercises across sessions 1–6) — the restructure changed nothing in the database, only how the source content is organized on disk.
- Largest content file dropped from 806 lines / 88KB (`ai-assisted-software-development.json`) to a largest single session file of ~17KB (`04-scaling-loops-and-worktrees.json`) — no file in the directory exceeds one session's worth of content, so the ceiling moves from "every session this topic will ever have" to "the sizing rule in ADR 0013," which already bounds a single session's length.
- Any future topic (new or existing) follows this same layout from the start — there's no longer a flat-file option to accidentally reach for.
