# ADR 0027: Topic/Section/Module rename and slug-based routing

## Status
Accepted

## Context
User feedback: routes like `/topics/42` and `/learning/221` tell you nothing about what you're learning at a glance. The ask was a naming convention that fixes this "at least up to the section level," where a *topic* is a top-level area like "Computer Science Foundations" or "Programming & Code Quality" and a *section* is "an area of learning under a specific topic" — the thing a learner actually opens.

Two clarifying questions resolved the design space before any code changed:
1. **Terminology**: the schema already had entities named `Domain` → `Module` → `Topic`, and the DB's own `Topic` (CURRICULUM.md's numbered 1-80 "module" granularity, e.g. "AI-Assisted Software Development") is a *different* thing from the user's "topic" (the top-level grouping, e.g. "AI & ML Engineering"). The user chose to rename the DB entities to match their vocabulary rather than keep the mismatch.
2. **Route depth**: the user chose the minimum scope — topic + section slugs in the URL — rather than extending human-readable slugs further down to the module/lesson level.

A further wrinkle, found while implementing: the product's own UI (the old `GET /topics` endpoint) already flattened past the old `Module` entity entirely — it returned `Domain → Topic` directly, skipping `Module`. CURRICULUM.md's own breadth map is also flat (a topic → a numbered list of 80 "modules", no further subgrouping), so `Module` was already a mostly-vestigial pass-through for everything sourced from `curriculum-map.json` (exactly one `Module` row per `Domain`, named after the domain). Only the 5 hand-authored lesson directories used `Module` for a real, distinct middle grouping (e.g. "Browser Fundamentals" under "Frontend Engineering"). This confirmed that "section" should map to the structurally-adjacent child of "topic" that the product actually surfaces — i.e. the DB's old `Topic`, not old `Module`.

## Decisions
1. **Rename, not restructure**: `Domain` → `Topic`, `Topic` → `Section`, `Module` stays `Module`. Every FK edge keeps pointing at the same rows; only names change. New hierarchy: `Topic → Module → Section → LearningSession`. `Module` is documented in its own docstring as an internal, currently route-unexposed grouping layer — not something this change tries to make meaningful everywhere, since CURRICULUM.md itself doesn't define real subgroups there yet for most of the map.
2. **One migration, hand-written** (`568f571b1e73`), not autogenerated — a straight `topics→sections`, `domains→topics` rename chain (no temporary table name needed, since it's a chain not a cycle: `Module` keeps its name throughout), plus FK column renames and a new `topics.slug` column backfilled by slugifying `name` (`Section.slug` already existed and needed no migration). All existing data — notes, study sessions, progress, leadership stories — is preserved; nothing is dropped and reseeded.
3. **Routes**: `/topics/<id>` + `/learning/<id>` → `/learn/<topic-slug>/<section-slug>` (section overview) and `/learn/<topic-slug>/<section-slug>/<session-id>` (lesson). The trailing session id stays numeric, per the chosen minimum depth. The section-overview page is looked up by **slug alone** (`GET /api/v1/sections/<slug>`), not by id — the slug is already a unique, human-readable identifier, so there's no reason to also carry a numeric id in that URL.
4. **Topic/section slugs in the URL are cosmetic, not validated against the lookup.** The actual lookup key is the section slug (unique) for the overview page and the session id for the lesson page; the topic-slug segment is never checked against the section's real parent. A stale or wrong topic slug in a shared link still resolves correctly, just with an inaccurate-looking URL. This is a deliberate simplification — there's no SEO or multi-user link-sharing concern here yet — not an oversight; validating and redirecting to a canonical URL is a clean follow-up if that ever changes.
5. **Cross-topic prerequisite links work correctly.** A section's prerequisites can belong to a different topic than the section they block (confirmed by a real example in the seeded data: `02-algorithms-problem-solving`'s prerequisites span both "Computer Science Foundations" and "Programming & Code Quality"). `PrerequisiteSummary` now carries its own parent `topic: {name, slug}` so the UI can always build a correct link, rather than assuming the current page's topic slug applies.
6. **`DEV_UNLOCK_ALL_TOPICS` renamed to `DEV_UNLOCK_ALL_SECTIONS`** for the same reason as everything else — it unlocks sections, not topics — updated consistently across `compose.yaml`, `config.py`, the dev-bypass banner, and tests.
7. **Split services/routes/tests along the new entity boundary** rather than keeping one oversized `topics_service.py`/`topics.py`/`test_topics.py`: `topics_service.py`/`routes/topics.py`/`test_topics.py` now cover only the curriculum-tree listing (`GET /api/v1/topics`, returning topics with nested sections); the status/lock/prerequisite computation and single-section detail moved to new `sections_service.py`/`routes/sections.py`/`test_sections.py` (+ `test_sections_service.py`).
8. **Content directories unchanged**: `content/curriculum/<section-slug>/` directory names and session-file naming stay as-is (they were always slugs, not entity names). Only the per-directory metadata file was renamed (`topic.json` → `section.json`) and re-keyed (`{domain, module, topic}` → `{topic, module, section}`), with a new `slug` field added under `topic` (generated by slugifying the topic name, matching the migration's backfill).

## Consequences
- Backend: `apps/api/app/models.py`, `schemas.py`, `seed.py`, `routes/{topics,sections,dashboard,leadership,learning_sessions}.py`, `services/{topics,sections,dashboard,leadership,learning_sessions,exercises,study_sessions}_service.py`, migration `568f571b1e73`. 76 tests pass (split/renamed across `test_topics.py`, new `test_sections.py`, `test_topics_service.py`, new `test_sections_service.py`, and renames throughout the rest of the suite); `ruff check` and `mypy` clean.
- Frontend: `topic-list.tsx`/`topic-overview.tsx` replaced by `curriculum-tree.tsx`/`section-overview.tsx`; `/app/topics/[id]` and `/app/learning/[id]` replaced by `/app/learn/[topicSlug]/[sectionSlug]/(page|[sessionId]/page)`; `lesson-content.tsx`, `dashboard-summary.tsx`, `story-form.tsx` updated for the renamed API fields (`section`/`section_sessions`/`section_id` in place of `topic`/`topic_sessions`/`topic_id`). 110 tests pass; `tsc --noEmit` and `eslint` clean.
- Content: 5 `topic.json` files renamed to `section.json` and re-keyed; `content/curriculum/README.md` updated.
- Docs: `CLAUDE.md`'s hierarchy line, `docs/ARCHITECTURE.md`'s modeling candidates and starter routes, and one `docs/PRODUCT.md` line updated to the new names. `docs/ROADMAP.md`'s Milestone 0/1 bullets were left as-is — they're a historical record of what was literally built at the time, same as earlier ADRs, not a live schema reference.
- Verified against the live dev stack with a real browser (Playwright): the migration applied cleanly against the running Postgres container (via the host venv — `docker compose exec api flask db upgrade` doesn't work here, same pre-existing limitation as ADR 0026's seeding note, since `compose.yaml` only bind-mounts `apps/api`); reseeded successfully; confirmed via `curl` that `GET /api/v1/topics` and `GET /api/v1/sections/<slug>` return the renamed shape; clicked through the actual homepage → section overview → lesson flow end to end, landing on `/learn/backend-apis/23-backend-architecture` and `/learn/backend-apis/23-backend-architecture/22`; confirmed the dev-bypass banner now reads `DEV_UNLOCK_ALL_SECTIONS` after recreating the `api` container to pick up the renamed `compose.yaml` env var (a running container doesn't inherit a `compose.yaml` env-var rename without recreation).
- Not done: slugs were not added below the section level (module, learning session) — per the user's explicit choice of minimum depth. `Module` remains unexposed by any route. Historical ADRs 0001-0026 were not rewritten to use the new terminology; they're a point-in-time record of decisions made under the old naming.
