# ADR 0037: Spaced-repetition review queue (Leitner boxes)

## Status

Accepted

## Context

`docs/ROADMAP.md` Milestone 6 ("optional future enhancements") names "adaptive review" and "spaced repetition" with no further design -- a clean slate, same situation as ADR 0036's multi-session projects. With Milestones 2-4 fully shipped, this was the most additive, lowest-risk item to pick up next: it needs no new foundational system (no auth, unlike "secure multi-user publication" or "entitlements," neither of which exist yet -- there's no `User` model at all) and no AI integration (unlike "AI-generated exercises," which `CLAUDE.md` already cautions against as premature). Two choices were confirmed with the user before building: scope is **exercises only** (not lesson content blocks, which have no correct/incorrect signal to schedule from), and the algorithm is a **Leitner box** system (discrete boxes with fixed intervals) rather than SM-2 (continuous per-item ease factors) -- simpler, deterministic, and easy to unit test without needing to fake the passage of time in exotic ways.

## Decisions

1. **New `ExerciseReviewState` model** (`exercise_id` FK, unique; `box: int`; `due_at`; `last_reviewed_at`), not a field bolted onto `UserProgress`. `UserProgress.advance_to` is structurally monotonic (it only ever moves a section's status forward); a Leitner schedule needs to regress on a wrong answer, which is a fundamentally different kind of state, so it got its own model rather than overloading one designed never to go backwards.
2. **Box intervals are a fixed list, `REVIEW_BOX_INTERVALS_DAYS = [1, 3, 7, 14, 30]`** in `app/services/exercises_service.py`. A correct answer promotes to `min(box + 1, len(...) - 1)`; an incorrect one resets to box 0. Only `multiple_choice` and `code` exercises participate -- `project` exercises are self-attested (ADR 0036) and have no single "submission" to key a review off of.
3. **No new submission endpoint.** The existing `POST /api/v1/exercises/<id>/submissions` already runs on every attempt, whether it's a learner's first attempt at an exercise or a later scheduled review of it -- `_record_review_outcome(exercise, is_correct)` is called from both `_submit_quiz` and `_submit_code` right alongside the existing `_advance_progress` call, using the same scoring result. This means answering a review looks and behaves identically, client and server, to answering the exercise for the first time; there's no parallel "review submission" code path to keep in sync with the real one.
4. **`exercise_summary()` was promoted from a private helper in `routes/learning_sessions.py` to a public function in `app/services/exercises_service.py`**, since the new review-queue route needs the exact same client-safe serialization (answer key stripped, hidden test case outputs stripped) that the learning-session detail route already had. `routes/learning_sessions.py` now imports and calls it instead of keeping its own copy.
5. **New `GET /api/v1/reviews/due`** (new `reviews_bp` blueprint) returns every `ExerciseReviewState` whose `due_at` has passed, oldest-due first, each with enough context (topic/section/learning-session title and slug) to both link back to its lesson and to let the client reuse the ordinary `ExerciseSwitch` component to render and answer it right there in the queue.
6. **Frontend reuses `ExerciseSwitch`/`ExerciseQuiz`/`ExerciseCode` as-is**, not a parallel review-specific exercise renderer. Both components gained an optional `onSubmitted?: (result) => void` prop (not called on a failed request), threaded through `ExerciseSwitch`; existing call sites that don't pass it are unaffected. The new `ReviewQueue` component uses it only to show a "Reviewed" badge next to an answered item -- it deliberately does *not* remove the item from the list, so the exercise's own inline correct/incorrect feedback (already built into `ExerciseQuiz`/`ExerciseCode`) stays visible rather than yanking the UI out from under the learner right after they answer.
7. **Surfaced via a top-level "Review" link on the homepage** (next to "Leadership" and "Dashboard"), not folded into the existing dashboard. A dedicated `/review` page keeps the feature's own empty/loading/error states simple and avoids modifying `dashboard-summary.tsx`, which is already tested and serves a different purpose (time/status overview, not an actionable queue).

## Consequences

- Backend: `pytest` 139 passed (129 before this slice + 10 new: Leitner box promotion/demotion across quiz and code exercises, project exercises never entering the schedule, the due-queue route's filtering/ordering/serialization, and that the answer key never leaks into a queue item). `ruff`, `black`, `mypy` all clean on touched files (two pre-existing line-length warnings in untouched code are not from this slice).
- Frontend: `vitest run` 211 passed (206 before this slice + 5 new, across `exercise-quiz.test.tsx`, `exercise-code.test.tsx`, and the new `review-queue.test.tsx`). `tsc --noEmit`, `eslint`, `prettier --check` all clean.
- Verified against the live dev stack (real Postgres, real browser via Playwright): submitted a real seeded quiz exercise correctly (box 0 -> 1), backdated its `due_at` via direct SQL to simulate the schedule coming due (no real multi-day wait needed to verify this), confirmed it appeared on `/review` with correct lesson context and box label, answered it again through the UI, confirmed the box advanced to 2 (due 7 days out) and the "Reviewed" badge appeared alongside the exercise's own "Correct!" feedback, and confirmed the homepage's new "Review" link. Zero console/page errors. All test-generated rows (`exercise_review_states`, `exercise_submissions`, `user_progress`) were deleted afterward, restoring the section to its pre-test state; the seeded exercise content itself was untouched.
- This is the first roadmap work picked up after ADR 0036 closed out the previously-current roadmap (Milestones 2-4); it comes from Milestone 6, which has no required ordering among its remaining items ("AI-generated exercises," "secure multi-user publication," "true backend-enforced entitlements," "payments").
