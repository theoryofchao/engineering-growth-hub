# ADR 0021: Add lint/format/type tooling to both apps

## Status
Accepted

## Context
Continuing the architecture sweep: the audit found zero lint/format/type tooling anywhere in the repo — no `pyproject.toml`/`ruff.toml`/`mypy.ini`/`.flake8` in `apps/api`, no `prettier` dependency or config in `apps/web`. Nothing currently enforces style or type consistency as the codebase grows.

## Decisions
1. **Backend**: added `ruff==0.17.1`, `black==26.10.1`, `mypy==2.4.0` to `requirements-dev.txt` (current-stable at implementation time, matching this repo's exact-pin convention). New `apps/api/pyproject.toml`: `[tool.ruff]`/`[tool.black]` at line-length 100, target `py312` (matching the Dockerfile's `python:3.12-slim`); `[tool.ruff.lint]` selects `E`/`F`/`I`/`UP`/`B` (pyflakes, pycodestyle, import-sort, pyupgrade, bugbear) as a reasonable, uncontroversial baseline.
2. **mypy scoped honestly, not aspirationally strict.** SQLAlchemy 2.0+ removed its mypy plugin (confirmed: `sqlalchemy.ext.mypy.plugin` no longer exists in the installed 2.1.4), and this codebase's models use the classic `db.Column`/`db.relationship` declarative style with no `Mapped[]`/`mapped_column()` type annotations anywhere — so mypy cannot resolve ORM attribute types at all without one. Running it as-authored produced 43 errors, nearly all variations of "`RelationshipProperty[Any]` is not iterable/indexable" — a structural limitation, not real bugs. Rather than silence these with scattered inline `# type: ignore` comments (which would hide the actual gap) or claim strictness the config doesn't have, `disable_error_code` turns off exactly the codes this limitation produces (`attr-defined`, `index`, `arg-type`, `no-any-return`, `name-defined`, `assignment`), documented in `pyproject.toml` with why. **Closing this gap for real requires migrating every model to `Mapped[]`-style typing** — a separate, materially larger piece of work (touches every column/relationship, real behavior risk under time pressure) deliberately left out of a tooling-addition slice, per CLAUDE.md's "don't attempt to build all phases in one task."
3. **Ran `black .` and `ruff check --fix .` once** across all of `apps/api` as part of adding the tooling, so it doesn't start the repo off already failing its own new checks. Reviewed the diff before trusting it: 33 of 41 files changed, entirely from two mechanical patterns (blank line after a module docstring; collapsing a line that now fits under 100 chars) plus import-sort fixes in the Alembic migration files — no logic changed, confirmed by the full test suite passing unchanged.
4. **Frontend**: added `prettier@3.9.10` and `eslint-config-prettier@10.1.8`. New `.prettierrc.json` (double quotes, semicolons, `trailingComma: "all"`, `printWidth: 100`, `tabWidth: 2`) matching the house style observed across every file read this session. Added `format`/`format:check` npm scripts. Wired `eslint-config-prettier` into `eslint.config.mjs` *after* the existing Next.js rulesets, so ESLint stops flagging anything Prettier already owns, instead of the two tools disagreeing.
5. **Ran `prettier --write src` once**, same reasoning as decision 3: 14 of 24 files changed, entirely line-collapsing/line-breaking to the new 100-char width — no logic changed, confirmed by the full Vitest suite, ESLint, and `tsc --noEmit` all passing clean afterward.
6. **Found and confirmed pre-existing, not introduced**: `npm install` surfaced 5 high-severity audit findings (`braces`/`micromatch`/`fast-glob` via `eslint-config-next`/`@next/eslint-plugin-next`). Verified via `git stash` that the same 5 findings exist identically on the pre-change tree — not a regression from adding `prettier`/`eslint-config-prettier`, and out of scope to fix here (would mean upgrading or patching Next's own eslint tooling).

## Consequences
- Backend: `ruff check .` and `black --check .` both clean; `mypy app` clean under the documented, scoped config (20 source files, 0 errors); `pytest` — 58 tests pass, unchanged by the formatting pass.
- Frontend: `npx eslint .` clean; `npx prettier --check .` clean; `npx vitest run` — 71 tests pass; `npx tsc --noEmit` clean.
- No schema, migration, business-logic, or API-shape changes in this slice — purely formatting and tooling configuration.
- Known, documented gap: mypy's SQLAlchemy-attribute blind spot (decision 2) stays open until/unless a future slice migrates `app/models.py` to `Mapped[]`-style declarative typing. Flagged here rather than silently worked around, so it isn't mistaken for "the code is now fully type-checked."
