# ADR 0036: Multi-session project exercises with self-attested checkpoints

## Status

Accepted

## Context

`docs/ROADMAP.md` Milestone 4's last bullet, "multi-session projects with checkpoint acceptance tests," had almost no prior design: `docs/PRODUCT.md` says only that a "short multi-session project" is one exercise type among several, "divided into Pomodoro-sized checkpoints with acceptance criteria," and `docs/ARCHITECTURE.md` named `projects`/`project_milestones` as unspecified future-only schema candidates. Two things were confirmed with the user before building: checkpoint "acceptance tests" are a **self-attested checklist** (not automated grading), chosen as the smaller, safer MVP that adds no new code-execution surface — directly relevant given `docs/THREAT_MODEL.md` (ADR 0035) was just written to scope exactly that kind of expansion carefully.

## Decisions

1. **"project" is a new `Exercise.type`**, alongside `multiple_choice` and `code` — not a new top-level `Project`/`ProjectMilestone` entity spanning multiple `LearningSession` rows. "Multi-session" describes how the *learner* works through it (returning across several of their own Pomodoro sessions), not a new curriculum data-model tier; `ARCHITECTURE.md`'s `projects`/`project_milestones` names were never more than placeholders, so there was no existing design to honor by building a bigger entity than the MVP needs. `definition_json` holds `{"checkpoints": [{"title": str, "acceptance_criteria": [str, ...]}, ...]}`.
2. **New `ProjectProgress` model** (`exercise_id` FK, unique; `checked_criteria: {"<checkpoint_index>:<criterion_index>": true, ...}`), edited in place like `Note`/`BlockCompletion` — **not** a new `ExerciseSubmission` row. Self-attestation is ongoing, mutable state, not a graded one-shot attempt; routing it through the existing `submit()`/`ExerciseSubmission` flow (designed for quiz/code scoring) would have been the wrong fit. A criterion's absence from the dict means unchecked, not `false`, so the shape never needs backfilling if a project's checkpoints are edited later.
3. **New `PUT /api/v1/exercises/<id>/project-progress`** (not the existing submissions endpoint) toggles one criterion at a time; `exercises_service.toggle_checkpoint_criterion` validates the exercise is actually type `project` and that the indices are in range for its own definition, and advances `UserProgress` to `"practiced"` once every criterion across every checkpoint is checked (mirroring how a correct quiz/code submission already does).
4. **Both existing two-way dispatch points became three-way**, not patched with a bolted-on branch: `_exercise_summary` (`routes/learning_sessions.py`) and `ExerciseSwitch` (frontend) previously assumed "not code = multiple_choice"; both now explicitly check for `"project"` before falling through to the quiz default.
5. **A real caught bug, not a hypothetical one**: `toggle_checkpoint_criterion`'s first-ever call for a given exercise constructed `ProjectProgress(exercise_id=exercise_id)` and immediately read back `progress.checked_criteria` — which was `None`, not `{}`, because SQLAlchemy's column-level `default=dict` isn't applied to an in-memory object until the next flush/commit. Caught via live `curl` verification (500 error), not by code review; fixed by passing `checked_criteria={}` explicitly at construction.
6. **One real seed-content example added**, not left purely hypothetical: a 3-checkpoint, 6-criterion project ("add a feature flag or config boundary to a real project") attached to `23-backend-architecture`'s third lesson, directly exercising that lesson's own feature-flag/config-boundary content — unlike ADR 0032 (reference links), this content is self-attested instructional text the agent could confidently author itself, not an external fact or URL requiring verification.
7. **Migration includes a hand-added `CheckConstraint` change Alembic's autogenerate didn't catch.** As with the earlier `code` type addition (`e47746f88a8c`), Alembic doesn't diff CHECK constraints automatically; the autogenerated migration only had the new `project_progress` table, so the `exercises.ck_exercise_type` drop/recreate was added by hand, following that same precedent.

## Consequences

- Backend: `pytest` 129 passed (119 before this slice + 10 new), covering toggle/untoggle, full-checklist progress advancement, out-of-range and non-project rejection, 404s, malformed-body rejection, serialization round-trip through the learning-session detail endpoint, and seed-time validation of a project's `checkpoints` shape.
- Frontend: `vitest run` 206 passed (199 before this slice + 7 new, across `exercise-project.test.tsx` and `exercise-switch.test.tsx`), covering checkpoint/criteria rendering, optimistic check/uncheck with the real PUT payload, the "Complete" badge once a checkpoint is fully checked, and rollback-on-failure. `tsc --noEmit`, `eslint`, `prettier --check` all clean.
- Verified against the live dev stack (real Postgres) with a real browser (Playwright): checked all 6 criteria on the real seeded project exercise, confirmed the 6/6 progress badge, all 3 "Complete" checkpoint badges, persistence across a reload, and that `UserProgress` for that section advanced to `"practiced"`. Zero console/page errors. All test-generated progress (the `project_progress` row and the `user_progress` row it created) was deleted afterward, restoring the section to `not_started` — the seeded exercise content itself stays, only the artificial self-attestation state was cleaned up.
- This closes out Milestone 4 (`docs/ROADMAP.md`) and, with Milestones 2 and 3 already done, the entire current roadmap.
