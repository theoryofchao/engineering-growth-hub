# ADR 0023: Backend Architecture (module 23) content

## Status
Accepted

## Context
Closing out the user's request for additional senior-level content, alongside the architecture-cleanup slices (ADRs 0019-0022). Module 23 "Backend Architecture" (Senior tier, prerequisites modules 10/20/21/25, subtopics 23.1-23.6 per `CURRICULUM.md:507-520`) had zero authored content, like 35 of the 36 Senior-tier modules. It's a direct, natural sequel to the System Design content already authored (ADR 0016/0017): those modules taught *designing* a system from requirements; this one teaches *structuring the code* of whatever gets built.

Investigation before writing: searched for a real engineering account of exactly this module's core tension (boundaries, domain modeling, service decomposition) rather than writing from generic pattern-book knowledge, matching this course's standing preference for named, real sources (ADR 0016's Atlassian citation, ADR 0009's Ronacher/Willison citations). Found and read in full Shopify Engineering's ["Deconstructing the Monolith"](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity) — a detailed, concrete account (a Rails codebase worked on by 1,000+ developers over a decade) of exactly the coupling problem this module exists to prevent, their explicit rejection of microservices in favor of an enforced-boundary modular monolith (their in-house tool Wedge, reorganizing code by business domain instead of technical layer), and a real payoff example (a legacy tax-engine swap made feasible by prior isolation work). This anchors sessions 1 and 3; session 2 (dependency injection, ports, transactions) is taught more conceptually, tying back to the same case study (Wedge's public-interface rule as a concrete port) rather than needing a second source.

## Decisions
1. **New topic directory** `content/curriculum/23-backend-architecture/`, `topic.json` matching module 23's existing `curriculum-map.json` entry exactly (domain, title, description, tier), so the three real sessions attach to the pre-existing WIP `Topic` row rather than creating a duplicate — verified post-seed via direct SQL (one `topics` row for slug `23-backend-architecture`, global counts unchanged at 17 domains / 81 topics).
2. **Three sessions, pairing the module's six subtopics consecutively**, matching ADR 0017's established pattern:
   - Sequence 1, "Boundaries and the Domain They Protect" (23.1, 23.2) — the coupling problem, hexagonal architecture's dependency direction, what a boundary buys you (Shopify's onboarding-cost and tax-engine examples), then domain modeling/invariants and the anemic-domain-model failure mode.
   - Sequence 2, "Wiring Dependencies and Drawing Transaction Lines" (23.3, 23.4) — dependency injection as what makes "replace a storage adapter while preserving tested domain behavior" (the module's own proficiency assessment) possible, ports-vs-adapters vocabulary tied to Wedge's public-interface rule, then transaction boundaries and recognizing when a design has silently assumed single-transaction consistency it doesn't have.
   - Sequence 3, "Splitting Services and Changing Behavior Safely" (23.5, 23.6) — Segment's and Shopify's own published accounts of rejecting/avoiding premature microservices, concrete criteria for when a network-service boundary actually earns its cost, then feature flags and config as the usually-cheaper alternative to a full service split.
3. **Sized and audited to the standing rule** (`content/curriculum/README.md`, ADR 0013): unlike ADR 0016/0017's first drafts (which ran short, 550-1050 chars/block), this draft landed within the 900-1800 char target on the first pass for 15 of 18 blocks; the 3 closing ("bottom line") blocks that ran slightly short were expanded with additional concrete substance, not padding. The answer-length-bias audit flagged 7 of 12 exercises on the first pass (58%, above the ~25% chance baseline) — rebalanced by lengthening distractor options to remove the "correct answer is uniquely longest" tell, bringing the flagged rate to 0/12.
4. **Added a `test_seed.py` assertion** mirroring the existing `ai_topic` check: module 23 has exactly 3 sessions with the expected titles and 6 content blocks each, 12 block-pinned exercises total, and attaches to the existing topic row without creating a duplicate. `test_topics.py`'s global domain/topic counts needed no changes, since module 23's `Topic` row already existed from `curriculum-map.json` — this only added sessions under it.
