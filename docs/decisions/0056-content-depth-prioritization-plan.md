# ADR 0056: Content-depth prioritization plan, and module 30 as its first pick

## Status

Accepted

## Context

With all 16 `CURRICULUM.md` domains now holding real lesson content (ADR 0039-0055), the user asked for the most logical plan to continue, now that domain breadth is exhausted. The actual remaining gap is much larger than it looked: of the 80 permanent module IDs, only 21 are authored. 59 modules across the 16 domains are still pure placeholders. Domain-breadth being "done" only means every domain has *a* foothold, not that the domains themselves are filled in -- the real next phase is module-breadth within those domains, which turns out to be the bulk of the remaining work.

## Decisions

1. **The prioritization method is the same prerequisite-graph analysis already used informally throughout this effort, made explicit and systematic**: parsed all 80 modules' prerequisites out of `CURRICULUM.md` programmatically, computed the set of currently-authored modules, and found every unauthored module whose full prerequisite chain is already satisfied -- 14 modules qualified immediately (3, 6, 9, 11, 12, 22, 24, 27, 28, 30, 38, 45, 50, 60).
2. **Within that set of 14, modules are further ranked by second-order unlock value** -- how many *additional* currently-locked modules become unlockable once a given candidate is authored -- rather than picking arbitrarily or by subtopic number. Module 30 (Architecture Fundamentals) ranked highest by a distinct margin: beyond unlocking module 31 directly, it is also a listed prerequisite of **two already-shipped modules** (33 and 71), both of which were built earlier in this effort under the partial-prerequisites exception. Authoring 30 retroactively completes both of those existing gaps at the same time as opening a new one -- a materially different kind of value than a module that only unlocks one new thing and nothing already in progress.
3. **Module 30 session 1 covers subtopic 30.1 (quality attributes and constraints)**, deliberately chosen as the opening session over 30.4 (ADRs and decision rationale) despite this repository's own `docs/decisions/` being an unusually strong, self-referential worked example for that subtopic -- quality attributes are the more genuinely foundational concept the rest of the module (tradeoffs, ADRs, evolutionary architecture) depends on understanding first. The ADR-specific session, with this repo's own decision log as its worked example, is deferred to a later session in this module rather than used here.
4. **Explicitly distinguishes quality attributes (negotiable, competing with each other) from constraints (fixed, non-negotiable)** as two different kinds of thing, not points on the same spectrum -- a distinction CURRICULUM.md's own subtopic list separates (30.1 covers both together) but that's commonly conflated in practice, which the session calls out directly with a worked example (debating whether to "prioritize" a legal data-residency requirement, as if it were negotiable).
5. **Ties back explicitly to two already-shipped sessions**: the "state it specifically enough to be falsifiable" discipline from module 71's hypothesis block, applied here to quality-attribute targets ("highly available" vs. "99.9%, measured monthly, $10,000/hour cost of missing it"); and the general "confirm/name explicitly before arguing about implementation" throughline running through modules 10, 49, 62, 63, and 71.
6. **No code exercise** -- architecture reasoning doesn't reduce to a gradable function, consistent with every other conceptual session this effort has built. **No external citation** either, unlike most recent sessions -- quality-attribute/constraint reasoning is foundational, uncontroversial architecture knowledge that doesn't need a named practitioner's framing the way a genuinely contested or counterintuitive topic (CAP theorem, the testing trophy, flame graphs) has in recent sessions.
7. **First-draft bias audit flagged 3 of 4 quizzes**, the heaviest flag rate of this effort tied with module 58's; rebalanced to 0/4 in one pass. All 6 blocks needed length-padding to clear 900 characters.

## Consequences

- `pytest` 139 passed (unchanged -- pure content; confirmed the section reused `Module` id 6, the same one modules 32/33 already use, rather than creating a duplicate).
- Verified against the live dev stack: section and lesson pages render, and the competing-attributes quiz was answered correctly through the real UI. Zero console/page errors. All test-generated rows deleted afterward.
- Module 30's own prerequisite chain (10, 20, 25) was already fully satisfied when picked -- no exception needed, unlike most of the prior several picks. Authoring it also retroactively closes out the partial-prerequisite exceptions used for modules 33 and 71, and opens module 31 (Architectural Styles) as newly unlockable.
- **Standing plan going forward**: re-run the same prerequisite-graph computation after each new module is authored (the unlock set shifts every time), and keep preferring the highest second-order-unlock-value candidate among the currently-unlocked set, over picking by subtopic number or arbitrary domain rotation. The next-highest-ranked candidates from this pass's computation, in roughly descending priority: 27 (Data Architecture, unlocks 26 and 36), 45 (Containers & Virtualization, unlocks 42 and 47), 3 (Computer Architecture, unlocks 4 and 7), with the remaining single-unlock and zero-unlock candidates (6, 9, 11, 12, 22, 24, 28, 38, 50, 60) picked up afterward as the graph continues to open up.
