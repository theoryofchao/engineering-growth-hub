# ADR 0038: Linked lists, stacks, queues, and deques content (module 01, session 2)

## Status

Accepted

## Context

With the roadmap (Milestones 2-4) and the first Milestone 6 feature both closed, the user asked for "more lesson content" with general curriculum breadth as the goal, not a job-search-specific push (confirmed explicitly -- the earlier Atlassian-interview framing from `docs/decisions/0016`/`0017` is now stale; see memory). Of the ~80 `CURRICULUM.md` modules, only a handful have any real authored content, and most of those (modules 01, 02, 15/frontend-engineering) have just one session against several planned subtopics. Module 01 (Data Structures) already had session 1 covering subtopic 01.1 (arrays/strings/two-pointer); 01.2 (linked lists, stacks, queues, deques) was the next unauthored subtopic in that same module and the most natural continuation, both because it's a direct prerequisite for nearly everything downstream (CURRICULUM.md's dependency graph) and because it picks up the exact cost-tradeoff thread session 1 started (array contiguity vs. pointer-based structures) rather than starting a new module cold.

## Decisions

1. **New session file** `content/curriculum/01-data-structures/02-linked-lists-stacks-queues-deques.json`, sequence 2, 25 minutes, `access_tier: "free"` -- matching session 1's conventions exactly (6 content blocks, opening/closing blocks with no exercises, one exercise per teaching block).
2. **Framed stacks/queues/deques as access disciplines on a representation, not as separate structures** -- a stack and queue are each just a deque with one end's operations unused, and either can be backed by an array or a linked list. This continues session 1's central idea (measure a structure by its actual operation costs, not by name) rather than introducing an unrelated new framing.
3. **One code exercise** (`isValidParentheses`, the classic bracket-matching stack problem) rather than attempting a linked-list-specific code exercise. A true linked-list code exercise would need the grading model (plain input values in, one output value out, per `content/curriculum/README.md`) to serialize custom node structures, which no existing exercise does and which this single session didn't need to invent new infrastructure for -- the stack/queue/deque *behavior* is fully exercisable on top of a plain array, which is also how most real stack implementations are actually backed.
4. **First-draft quiz options were rebalanced for the answer-length-bias check** -- 2 of 3 multiple-choice exercises initially flagged (correct answer was the uniquely longest option), brought to 0/3 by shortening the correct option and lengthening the distractors without changing their technical content. Consistent with the now-recurring pattern noted in ADR 0012/0015/0016/0017: budget an iterative rebalancing pass as normal, not a sign of a mistake.
5. **Seeding must run from the host venv, not `docker compose exec api flask seed`.** Discovered during this slice: `compose.yaml`'s `api` service only bind-mounts `./apps/api` to `/app`, so `content/curriculum/` (at the repo root, a sibling of `apps/`) isn't visible inside the container at all -- `app/seed.py`'s `CONTENT_DIR = Path(__file__).resolve().parents[3]` runs out of path segments inside the container and raises `IndexError`. `flask seed` only works from the host's `apps/api/.venv` (the same environment `pytest` already runs from), with `DATABASE_URL` pointed at `localhost:5432` per `.env.example`. Flagged as a new dev-environment quirk alongside the existing root-owned-`.next` and container-node_modules ones.

## Consequences

- `pytest` 139 passed (unchanged -- pure content, no new backend tests needed; no test hardcodes module 01's session count). The answer-length-bias audit script from `content/curriculum/README.md` now reports 0/3 flagged for this session.
- Verified against the live dev stack: the section page lists both sessions, the new lesson page renders all 6 blocks, the linked-list quiz was answered correctly through the real UI (radio selection -> submit -> "Correct!"), and the `isValidParentheses` code exercise's full answer key (6 cases, including the 4 hidden ones) was independently re-derived by running the reference algorithm in Node and confirmed to match the shipped `expected_output` values exactly, then confirmed correct end-to-end via a direct submission to `POST /api/v1/exercises/<id>/submissions`. (Typing a multi-line solution into the live Monaco editor via Playwright's raw keystrokes was not reliable -- Monaco's own auto-closing-bracket behavior mangles naively-typed code with braces/parens -- so correctness was verified via the API directly instead, consistent with the code exercise's actual trust model of comparing submitted output values server-side.) Zero console/page errors. All test-generated `exercise_submissions`, `exercise_review_states`, and `user_progress` rows were deleted afterward.
- Module 01 (Data Structures) is now 2 of 6 subtopics authored (01.1, 01.2); 01.3 (hash maps/sets) is the natural next session if this module continues.
