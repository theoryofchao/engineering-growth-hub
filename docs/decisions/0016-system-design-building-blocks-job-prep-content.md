# ADR 0016: System Design Building Blocks content, scoped for an active job opportunity

## Status
Accepted

## Context
User request: a recruiter reached out about a Senior Fullstack Software Engineer role at Atlassian (two openings: 50/50 fullstack and backend-leaning), emphasizing "massive multi-tenant scale and low-latency microservices," plus a related JD emphasizing technical-direction ownership, correctness/robustness/performance/customer-impact tradeoffs, production reaction/bug-fixing, code review, and mentorship. Asked to build lesson content that improves the odds of landing it.

Investigation before writing content:
- `CURRICULUM.md` already has module 32 ("System Design Building Blocks," subtopics 32.1–32.6) sitting almost exactly on the recruiter's stated theme: 32.5 is "Rate limiting and throttling," 32.6 is "Identity and multitenancy infrastructure," and 32.4 ("Caching and search") underlies "low-latency" generally. No content existed for this module yet — like nearly all of the 80-module map, only `ai-assisted-software-development` and `frontend-engineering` had real lesson content before this change (confirmed via `content/curriculum/`'s directory listing and `load_curriculum_map`'s WIP-topic behavior).
- Searched for Atlassian's own public engineering writing on this exact theme rather than relying on generic multi-tenancy material, matching this course's standing preference for named, real sources over generic advice (the same standard applied to the Ronacher/Willison/METR citations and the two Claude Code guides). Found and read in full Atlassian's engineering blog post on their Tenant Context Service (TCS) — a real, detailed, numbers-backed account of exactly the "multi-tenant scale and low-latency microservices" problem, including concrete production incidents and fixes (DynamoDB behavior under load, an ELB→ALB tradeoff, a Guava→Caffeine caching-library change, a client-sidecar pattern) and real latency/availability figures (tens of thousands of req/s, 4–5 nines availability target, ~0.7ms client-observed p99 after the sidecar rollout).
- Scoped to a tight, high-leverage subset of module 32 rather than all 6 subtopics: caching (32.4, caching only — deliberately not "search," which is a different concern bundled into the same subtopic number), rate limiting/throttling (32.5), and multitenancy infrastructure (32.6). Subtopics 32.1–32.3 (load balancers/proxies/gateways, CDN/object storage, messaging/queues/streaming) remain unauthored, left for a future slice, per CLAUDE.md's instruction not to build all phases in one task.

## Decisions
1. **New topic directory** `content/curriculum/32-system-design-building-blocks/`, matching module 32's existing slug/title/description/tier from `curriculum-map.json` exactly in its `topic.json`, so the real sessions attach to the already-existing WIP `Topic` row created by `load_curriculum_map` rather than creating a duplicate. Verified post-seed via SQL that no duplicate `Domain`/`Module`/`Topic` rows were created.
2. **Three sessions**, in a deliberate build-up order:
   - Sequence 1, "Caching and Invalidation at Scale" — cache layer selection, TTL vs. event-based invalidation, cache stampede mitigation, and the client-sidecar pattern, each illustrated with a specific, cited detail from the TCS case study (its SNS-based invalidation timing, its Guava→Caffeine fix, its reported 0.7ms client p99).
   - Sequence 2, "Rate Limiting, Throttling, and the Noisy Neighbor Problem" — token bucket vs. leaky bucket, per-tenant/per-tier scoping (citing Atlassian's own public point-based rate-limit design, which scopes by app identity/tenant/tier specifically to contain noisy neighbors), bulkheading, and why autoscaling alone doesn't fix a shared-resource bottleneck.
   - Sequence 3, "Multitenancy at Scale: A Real Tenant Context Service" — the three tenant-isolation models (shared-schema, schema-per-tenant, database-per-tenant) and their tradeoffs, then the TCS case study itself end to end: the problem it solves, its extreme availability/latency requirements and why they justified its architecture, what actually broke under real load, and the sidecar-cache payoff — closing with an explicit prompt to be able to name which of isolation/rate-limiting/caching depends on which of the others, matching the JD's "evaluate tradeoffs" and "guide technical direction" language directly.
3. **Named Atlassian specifically, with a citation**, rather than anonymizing the source — the content is drawn from Atlassian's own public blog post, and naming it is both accurate and the most interview-relevant framing available: a candidate who can discuss the company's own published engineering account specifically, not just system design in the abstract, is exactly the differentiated answer the JD's "guide technical direction" and interview-signal bullets reward.
4. **Sized and audited to the same standing rule** (`content/curriculum/README.md`, ADR 0013): all three sessions needed two rounds of padding (initial drafts ran short, 550–1000 chars per block against a 900–1800 target) and the answer-length-bias audit flagged roughly half the exercises on the first pass across all three files, requiring iterative rebalancing — consistent with how much rebalancing effort ADR 0012/0015 also needed, suggesting this is a real, recurring cost of first-draft content rather than a one-off.

## Consequences
- `pytest`: 29 tests pass unchanged — no test hardcodes a session or topic count for `32-system-design-building-blocks`, so no assertion updates were needed this time (unlike ADR 0011/0012/0015's work on the AI-assisted-development topic).
- Verified against the live stack: reseeded and confirmed via direct SQL that all 3 sessions landed with the expected block/exercise counts (6/6/7 blocks, 4/4/4 exercises), confirmed no duplicate domain/module/topic rows were created by attaching to the pre-existing WIP topic, and confirmed via the live API that content renders correctly with no answer-key leakage.
- Did not build subtopics 32.1–32.3, or module 33 (System Design Methodology — the explicitly interview-shaped module: functional/nonfunctional requirements, capacity estimation, bottleneck analysis) or modules 35–39 (Distributed Systems), all of which are natural, closely-related follow-ups for the same job-prep goal — flagged for a future slice rather than attempted here.
- `CURRICULUM.md`'s own `Status: not-started` and `Content` fields for module 32 were not updated in this pass — consistent with the project's existing, previously-noted staleness in that metadata (see ADR 0012's investigation notes on module 70), not something newly introduced here.
