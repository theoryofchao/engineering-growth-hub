# ADR 0028: Code exercises, graded without Flask ever executing learner code

## Status

Accepted

## Context

`docs/ROADMAP.md` Milestone 4 ("Monaco editing; isolated JS exercise evaluation, tests, timeouts, failure UX... design a threat model before enabling arbitrary public code execution") is next after Milestone 3's first slice (leadership, ADR 0024). The user asked to pull this forward now, ahead of finishing Milestone 3's remaining rubric/scenario-tree work, specifically wanting a LeetCode-style coding exercise backed by `CURRICULUM.md`'s already-defined-but-empty modules `01 — Data Structures` and `02 — Algorithms & Problem Solving`.

`CLAUDE.md` is explicit and non-negotiable: Flask must never execute learner-submitted code, with or without infrastructure secrets. Today's only exercise type, `multiple_choice`, is graded with exactly that constraint already satisfied — the server holds `correct_index` and compares it to a submitted index, never running anything. The design problem this ADR solves is generalizing that same trust model to code exercises, not inventing a new one.

## Decisions

1. **Code runs only in the browser**, in a Web Worker, never in Flask. No iframe/CSP sandboxing was added — a Worker already has no `document`/cookie/`localStorage` access, and the only realistic threat at this stage is the learner's own infinite loop or runaway memory use, not a malicious third party. Defeating `fetch`/`importScripts` inside the worker, and the Python runner, are explicitly out of scope here — that's the separate, security-reviewed milestone `ROADMAP.md` itself calls for before enabling arbitrary *public* code execution. This is a personal, single-user tool today; that threat model will need revisiting before any multi-user exposure.
2. **Grading generalizes `selected_index == correct_index` to per-test-case `actual_output[i] == expected_output[i]`.** `Exercise.definition_json` for `type="code"` stores `visible_test_cases` (input + expected output, shown to the learner so they get feedback while coding) and `hidden_test_cases` (input + expected output, output **never** sent to the client pre-submission). The client's Worker runs the learner's function against every case's *input* — visible and hidden — producing `actual_output` per case, then POSTs that array (fixed visible-then-hidden order) to the existing submissions endpoint. The server does a plain Python `==` comparison against its own stored expected outputs and returns a score. It never re-runs, parses, or inspects the learner's code in any way — only the resulting values.
3. **`Exercise.type`'s check constraint widened** from `'multiple_choice'` to `'multiple_choice', 'code'` (migration `e47746f88a8c`, `down_revision = 568f571b1e73`). No new columns — `definition_json`/`result_json` (already JSON) absorb the new shape.
4. **`ExerciseSummary` and the submission result became discriminated unions** (`app/schemas.py`, keyed on `type`/`kind`) rather than one flat model with more optional fields. A hidden test case's client-facing type has no `expected_output` field at all — a leak is a type error, not a runtime "remember to strip this key" bug. The hidden cases' expected outputs *are* included in the submission response after grading, symmetric to `correct_index` being revealed today.
5. **Two content-authoring simplifications**, documented in `content/curriculum/README.md`, needed to keep grading a single equality check instead of reintroducing judging logic server-side:
   - **Canonical output required** — e.g. "return indices in ascending order" — no order-insensitive/fuzzy comparison.
   - **Return the full graded result, don't rely on in-place-mutation-only grading** — e.g. `removeDuplicatesInPlace(nums)` returns the deduplicated array itself, not just a length the judge would otherwise have to inspect the mutated argument for. This is a deliberate scope simplification, not solved generally.
6. **Accepted, explicit non-goal: a learner can bypass the Worker via devtools and hand-type a submission.** For visible cases this is exactly as easy as guessing `selected_index` today. For hidden cases it's harder *before* a first attempt (the client never receives hidden expected outputs ahead of submission) but converges to the same "post-reveal" situation after one wrong, revealed attempt — which is pedagogy (see your mistake, learn from it), not a flaw. This is a single-user personal learning tool; defending against the user cheating themselves was never a goal, same posture as the existing quiz type.
7. **Web Worker instantiated from a Blob URL** (`new Worker(URL.createObjectURL(new Blob([...])))`), not a bundler-native `new Worker(new URL(...))` — this app runs on Turbopack (`apps/web`'s dev/build pipeline), and the Blob URL approach is bundler-agnostic rather than depending on Turbopack's own worker-asset handling. **Verified directly against the running dev stack with a real browser** (see Consequences) rather than left as an assumption. One fresh Worker per test case (not one worker reused across cases) — simpler than reusing-unless-timeout, and still guarantees one infinite loop only kills that one case's feedback, since each case gets its own Worker and timeout regardless.
8. **Prerequisite edges temporarily dropped.** `CURRICULUM.md` lists module 1 depending on module 8 and module 2 depending on modules 1, 6, 8 — but modules 6 and 8 have zero seeded content and can never reach `practiced`, which would leave the new sections permanently locked under normal navigation. `content/curriculum/curriculum-map.json` was edited so module 1 has no prerequisites and module 2 depends only on module 1 (the one edge that's both pedagogically real and actually satisfiable). This is a temporary divergence from `CURRICULUM.md`'s own documented graph, to be restored once modules 6/8 get real content — `CURRICULUM.md` itself was left unchanged since it describes the intended long-run structure, not what's currently seedable.
9. **Content seeded**: one session each under `01-data-structures` ("Arrays, Strings, and the Two-Pointer Pattern": 1 quiz + 2 code exercises — `reverseInPlace`, `isPalindrome`) and `02-algorithms-problem-solving` ("Two Pointers and Sliding Windows on Arrays": 3 code exercises — `twoSumSorted`, `removeDuplicatesInPlace`, `maxSubarraySumFixedWindow`), sized per the existing 6-7 block / 900-1800 character sizing rule (ADR 0013).

## Consequences

- Backend: `pytest` — 85 passed (76 before this slice + 9 new: code-grading unit tests covering all-pass/partial-pass/wrong-length/error-sentinel/hidden-reveal paths, plus route and serialization integration tests). `ruff`/`black`/`mypy`: clean.
- Migration applied and rolled back symmetrically against the real Postgres dev instance (`flask db upgrade` / `downgrade` / `upgrade` again, confirmed via `flask db current`).
- `flask seed` run twice against the live dev DB to confirm idempotency; content loads correctly, `01-data-structures`/`02-algorithms-problem-solving` now show `has_content: true` where several other tests previously treated them as the standing "WIP, no content" example (now repointed at `03-computer-architecture`, which is still genuinely empty).
- Frontend: `vitest run` — 128 passed (110 before + 18 new, covering the worker-source evaluator directly, the fake-Worker-driven timeout/error/success paths in `code-runner.ts`, and the `ExerciseCode` component's Run/Submit/error/focus-management behavior). `tsc --noEmit`/`eslint`/`prettier --check`: clean. `@monaco-editor/react` added to `apps/web/package.json`; `npm audit` flags a transitive `dompurify` advisory inside `monaco-editor` with no non-breaking fix currently available upstream — tracked as a known, accepted dependency risk to revisit on a future `monaco-editor` version bump, not exploitable via this component's actual usage (no attacker-supplied HTML is ever passed through Monaco's markdown/hover rendering here).
- Verified end-to-end against the live dev stack with a real browser (Playwright): loaded the seeded lesson, drove Monaco directly via its exposed `window.monaco` API (keystroke simulation against this Monaco version's EditContext-based input handling proved unreliable for E2E automation — a test-tooling finding, not a product bug), ran a correct `reverseInPlace` solution (Run showed 2/2 visible cases passing with no network call; Submit posted to the real API and returned "All test cases passed!" with the 3 previously-hidden cases now revealed), and separately ran a deliberate `while (true) {}` submission for `isPalindrome` — each visible case timed out and reported "Timed out" cleanly within its own 2000ms budget, with zero console/page errors and the browser tab never hanging. Confirmed via the live dashboard endpoint that the correct submission advanced `01-data-structures`'s progress to `practiced`.
- Not done: Python exercises, iframe/CSP-level sandboxing, and any defense against the learner bypassing the Worker via devtools — all explicitly out of scope per the Decisions above. `README.md`'s top-level "Status" line (still describing Milestone 0) was already stale before this change and wasn't touched here.
